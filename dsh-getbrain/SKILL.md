# 得到大脑（Get笔记）整理纪律

> 本文件既是「说明书」，也是本 Bundle 的一部分。`dsh-getbrain/` 目录整体是一个正式 Cordis 插件：
> `index.js` 注册 `getnote_*` 模型工具，`client.js` 在「设置」里提供 Mgetbrain 侧边栏配置表单，
> `gn.py` 是真正干活的官方 OpenAPI 客户端，本文件是给 agent 看的纪律。装了插件后可用 `getnote_guide` 随时读回。

> **定位（2026-11-20，v2.10.0）**：这**不是**多人协作 / 多用户 / 团队知识库插件。
> 事实是**一个 Get笔记 账号、三个自然人共用**：我（工作与 AI 思考）、孩子（学习与升学）、
> 老婆（部门会议与客服质量），外加大量全家一起读的摘录。
> **维护分类的只有一个人（用户本人）**；agent 的职责是**先分清是谁的内容**，再谈分类。
> 不做账号体系、不做权限、不做冲突合并 —— 不要往那个方向设计。

## 铁律（不可绕过）

1. **只用官方 OpenAPI，通过 `dsh-getbrain/gn.py`（或 `getnote_*` 工具）**。禁止逆向网页接口、第三方 MCP、直接手写 curl 批量删改。
2. **先下载 + 备份**：`getnote_download`（全文字到 `dataDir/downloads/`）供人先分析决策；
   任何写操作前必须 `getnote_backup`（Phase 0 全量只读快照到 `dataDir/snapshots/`），验收前不删。
3. **默认只读**：`doctor / download / backup / list / search / topics` 只读；写命令不带 `--apply` 一律只是 DRY-RUN。
4. **先出方案再动手**：基于下载/快照产出 dry-run 整理报告 + `plan.json`，**用户确认后**才 `getnote_apply`（内部仍需 `--confirm CONFIRM`）。
5. **删除按不可逆对待**：官方 FAQ 自列 bug「删除后直接彻底删除、未进回收站」。优先降级为「打归档标签 + 移入待清理知识库」；真删需二次确认 + `--i-understand-deletion-may-be-permanent`，并去 App 回收站核验。
6. **凭据安全**：在「设置 → Mgetbrain」→「账号凭据」里输入 API Key / Client ID，点「保存凭据」——它写入 DSH 凭据库 `$DSH_HOME/.credentials.yaml`（仅本机该用户可读），**不进组合树**。也可用环境变量 `GETNOTE_API_KEY` / `GETNOTE_CLIENT_ID` 或 `apiKeyFile`。不回显、不写聊天/日志/仓库。面板保存即时生效（无需重启）。

## 统一数据目录（dataDir）

默认 = **仓库同级的 `data-getbrain`**（本机 `C:\dsh\data-getbrain`，首次运行自动创建）。
它在任何 Git 仓库之外：不进同步、不进插件包，数据完全在本机自己掌控。
插件 Config 的 `dataDir` 填了就优先用它；留空就是上面的默认值。其下：
**默认只下载全文字**；音频/视频二进制为硬约束永不下载；图片需 `media.images=true` 或 `download --with-images`。

## 关键坑

- **先分人，再分类**：这个账号里混着三个人（我 / 孩子 / 老婆），判归属一律用
  `gn.py personas`，**不要用关键词自己猜**。关键词天然串台（「国航」既是我的国航数字化
  也是老婆的国航客服中心，「训练」既是模型训练也是击剑训练），纯关键词判 269 篇自己记的
  只能判出 我 67 / 孩子 81 / 老婆 20 / 歧义 4 / **未知 97**。归属靠「知识库 + 关键词 +
  手动钉住」三种信号叠加；判不出来就留在「未知」等人指，不硬猜。详见 README §11.14。
- `note/update` 的 `tags` 是**替换覆盖** → 分类一律用 `tag_add`。
- 雪花 ID 一律字符串；`HTTP 200 且 success:false` 仍是失败。
- **层级不在服务器上**：知识库（topics）是**平**的，没有 parent/folder；`knowledge/detail` → 404。
  「知识库→目录→书→讲」只能由 `gn.py inventory` 从本地镜像重建（课题标签 = 目录，标题《》 = 书）。
- **子笔记只能一层且不可逆**：`parent_id` 创建后不可改（`immutable_parent_relation`）、无法摘除、
  无法列子列表（相关端点全 404），**删父会连带丢子**（子笔记变 `10500 note_not_found`）。
  所以不要把一整本书的划线搬成子笔记，用标签 + 知识库分组。
- **侧边栏写操作走“三层门”**：`/plan`（只写计划文件、白名单四 op）→ `/apply` 默认干跑
  → 真写需 `confirm:"APPLY"` + `dryRun:false`，>200 个动作还要 `allowHighRisk`。
  删除**已接进面板**（2026-11-19，四道闸门：默认收起 / 勾确认 / 干跑 / 二次点真删），命令行仍可用 `gn.py note-delete --note-id <id> --apply --i-understand-deletion-may-be-permanent`。删除**不混进批量计划**：一次只删一条。
- **`kb_batch_add` 是“加入”不是“移动”**：不会把笔记从原知识库移走；要去掉旧的得 `kb_remove`。
  `tag_add` 同理是追加，不是覆盖。
- 列表 `cursor` 分页每页 20；详情在 `data.note`；`recall` 的 `top_k` 非全量，判重别只靠它。
- 限流 ~2 QPS（可配 `minInterval`）、读 2万/日 20万/月；429 按 `reason` 退让。订阅库只读；每天最多建 50 库。
- 会员是硬前提（否则 `10201 not_member`）。
- **面板保存的配置即时生效**（volatile 字段就地写回运行中的插件）。只有改 `index.js`（Host 模块已入内存）或 `package.json` 的 `dsh.client` 才需重启；改 `client.js` 由 client-hmr 热重载。
  **注**：本条已过时/需修正——实测改 `index.js` 新增的**路由**必须重启 App 才生效
  （进程内存里的旧注册表不会热更）；改 `client.js` 刷页即可；`gn.py` 是子进程，改完即生效。

## 撤销（2026-11-18 新增）

写错分类可以回退，但**前提是写前拍了快照**。

- `gn.py undo-snapshot --plan <plan>`：只读，把要改的每条笔记的**原归属**（知识库+标签）存成 `state/undo-<stamp>.json`。
- `gn.py undo --plan <undo文件> --confirm UNDO [--dry-run] [--allow-large]`：按**状态收敛**回滚。
- 侧边栏 `/apply` 真写时**自动**先拍快照；拍不到就**中止写入**（宁可这次不改，不能改了无法回退）。

为何不能只靠反向操作：`kb_batch_add` 是“加入”不是“移动”，天真地 `kb_remove` 会把原本的归属也踢掉；
`tag_add` 同理。必须知道“改之前是什么样”。详见 `docs/UNDO-DESIGN.md`。

边界：只还原**归属**，不还原正文（`note_update` 的内容旧文不存）；`note_delete` 不进撤销体系。

## AI 动作：发芽 / 审问 / 连线（2026-11-18 新增）

**平台端只能查不能生成**（实测：`GET /resource/note/sprout?id=` 返回 `has_sprout`；POST 同路径 404；
13 个其他 AI 端点全 404）。所以：

- `gn.py sprout --note-id <id>`：查平台已有发芽内容（只读）。
- `gn.py context-pack --note-id <id> [--limit N]`：把「中心笔记 + 同系列其他讲 + 跨系列相关段落 + 关键词」
  拼成给 AI 的素材包，**纯本地、不发网络请求**。
- `gn.py prompts [--ensure] [--name sprout|interrogate|link]`：提示词存在 `<dataDir>/prompts/`，
  首次自动创建，之后**用户改文件就生效，不用改代码**。

“发芽”（用户原话：「让发芽一下，看能不能把沟通和另外两个做一个补充」）= 基于已有记录联想补全、指缺口。
“审问” = 出题逼真理解（不给答案），对应渐进式总结 Layer 4。“连线” = 辨别真假相关。

三者**都不自动写入**：结果只展示，用户自己决定要不要动手。

为何需要 context-pack：只给一条笔记就发芽，AI 会泛泛而谈；它需要知道这条在哪个系列里、
别讲了什么、别处哪里聊过。关键词质量踩过三次坑（详见 `docs/AI-ACTIONS.md` §3）。

## 合并 / ID 表 / AI 提纯包（2026-11-19 新增）

目标里的「合并笔记」「AI 能读懂我」这两块，本轮补齐。

### 合并笔记

`gn.py merge <id1> <id2> [...] [--title T] [--tags ...] [--style sections|divider] [--show] [--apply --i-understand-new-id]`

平台**没有合并接口**，只能读旧正文 → 写一条新笔记。必须记住的代价：
**新笔记是全新 `note_id`，指向旧 ID 的引用全断**。所以默认**一条旧笔记都不删**。

- 不带 `--apply`：只预览（条目、字数、标题、将创建的正文）。退出码 0。
- `--apply` 但没 `--i-understand-new-id`：拒绝，退出码 3。
- 少于两条：退出码 2。
- 任何一条读不到正文：**整单中止**，不静默跳过（退出码 3）。

每条来源块会写进新正文（`## 来源：<标题>` + `note_id` + 原始链接），
并在 `state/merge-<时间戳>.json` 留一份「这条新笔记是从哪几条拼的」。

### ID 表（名字不要再当外键）

`gn.py ids [--json]` — 扫镜像重建 `state/ids.json`，报三类问题：

| 类别 | 含义 | 实测 |
|---|---|---|
| `id_renamed` | 一个 id 多个名字 | 0 组 |
| `same_name_multi_id` | 一个名字多个 id | **1 组：标签「AI」→ 36117013 / 36111209** |
| `kb_tag_overlap` | 知识库名与标签名重复 | 110 个（结构性冗余，不一定是错） |

**「AI」那组是真 bug**：任何按名字做标签操作的地方都只会命中其中一个，漏掉另一个。
跑一次 2 秒（纯本地，不耗配额）。

### AI 提纯包

`gn.py agent-brief [--days N] [--top 12] [--recent 10] [--top-todos 40] [--json]`

给 AI Agent 读「用户在忙什么」，四块：**没合上的待办 / 时间主要花在 / 自己的主题 / 最近动态**。

关键设计：把 4052 篇课程摘录和 269 篇自己记的**分开数**。
摘录按来源数会占据头部（「万维钢·精英日课6」926 篇），但自己的计数是 0 ——
那是阅读记录，不是工作方向。`own_topics` 只统计自己记的那 269 篇。

实测：431 条没闭合的待办；269 篇自己记的里 **219 篇没进任何知识库**（81%），
60 篇只有「得到」或载体标签。剔除无效标签后真实主题只剩高考志愿填报、强基计划、
AI、航空服务、击剑、民航服务等不到 10 个。

标签过滤**复用 `_content_tags()`**（它负责剔掉「得到」和载体标签），不要另写一遍：
两处规则一旦分叉，数字就会对不上。剔除前后「未归」从 13 篇变成 49 篇——
之前那个 13 是被「得到」标签蒙住了。

待办只从 `### 📋 待办事项` / `### 📝 待办事项` 小节抽纯列表行，
**不全文搜「待办」**（普通正文里这个词出现很多次，全搜会误判）。

### 三条新路由

| 路由 | 方法 | 闸门 |
|---|---|---|
| `/plugins/getnote/merge` | POST | `confirm:'MERGE'` + `acknowledged:true`，默认干跑 |
| `/plugins/getnote/ids` | GET | 无（只读） |
| `/plugins/getnote/brief` | GET | 无（只读，参数 `days`/`top`/`recent`） |

> 踩坑记录：`runGn` 返回的 `code` 是**字符串** `'OK'` / `'EXIT_1'`，
> 不是数字。写成 `ok: out.code === 0` 会永远 false，把成功报成失败。统一用 `out.ok`。

## 知识管理立场（为何功能长这样）

完整推导见 `docs/PKM-THEORY.md`。核心事实与结论：

- 库里 **94% 是课程划线摘录（4052 条），只有 6% 是你自己的记录（269 条）**。
- 所以两堆要**分开对待**：划线按「来源形状」组织（机器做），自己的记录按「可行动性」组织（人+AI）。
- 不要把这 4052 条按主题重分类进 PARA——一门课能横跨多个主题，重分类等于人工读 4052 条。
- 树上做「浏览与批量搬运」，**不要在树上做思考**（层级结构不适合发现跨域联系）。
- 真正缺的不是更花的分类树，而是渐进式总结的 **Layer 2–4**（加粗/高亮/用自己的话）。
## 标准流程

```
getnote_guide                       # 读本纪律（层级/子笔记限制也在里面）
```

完整命令、计划格式、迁移说明见 `C:\dsh\dw-plugin\dsh-getbrain\README.md`（插件目录内，不在数据目录）。

> 说明书管「决策纪律」，`gn.py` 的代码闸门管「执行」——双保险，任一层被绕过另一层仍拦得住。

## 检索与发布（v2.9.0 起）

整理完的书库要能**查**、能**给别人读**，这两件事走本地，不联网、不耗配额。

```
gn.py index                      # 建/刷新本地全文索引（sqlite FTS5，纯本地）
gn.py find "关键词" --kb <库名>   # 检索，--json 给程序用
gn.py publish --kb <库名>        # 导出成自包含静态站点
```

**什么时候用它，而不是官方 `search`：**

| 想要 | 用哪个 |
|---|---|
| 语义相近（「升学考试」找「高考」） | `gn.py search`（官方 recall，Top-10、联网、耗配额） |
| 字面命中、要全量、要按库/类型/归属过滤 | `gn.py find`（本地，无限条、离线、可按库/类型/`--owner` 过滤） |

`find` 是**字面检索**，不是语义检索。搜「高考」不会命中「升学考试」。
反过来它不会漏——真出现过这个词就一定搜得到，而且带原始链接。

**发布产物**：`publish` 导出 `index.html` + 每篇一页 + `search.html`（纯前端搜索）。
零外部依赖，双击就能看，整个目录可以直接发人。**不含凭据。**

## 向量检索、镜像对账与摘要（v2.11.0 起）

```
gn.py vec-index                 # 建本地稀疏向量索引（TF-IDF + sqlite，纯本地）
gn.py vec-search --q <词>       # 余弦检索，与 find 的字面检索互补
gn.py mirror-check              # 本地镜像 vs 线上 list 对账（只读，耗读配额）
gn.py summarize                 # 渐进摘要 L3 自动 + L4 模板，只写 <dataDir>/summaries/
```

- **`vec-search` 不是语义检索**（是 TF-IDF 稀疏向量）：同义不同词仍会漏；要语义用官方 `search` 或 `dsh-rag`。
- **`mirror-check` 是写操作前的对账**：本地算错 = 批量打错线上，先对账再动。
- **`summarize` 不写回平台**（写正文是 `note-update` 的覆盖语义，不可撤销）。
- **`node tools/structure-check.mjs`** —— 改过 `client.js` 之后必跑，专拦「不报错但界面就是不对」的结构缺陷。
- 标签/知识库**按名字操作前先跑 `gn.py ids`**：重名会静默命中其中一个（实测标签「AI」有两个 ID）。

## 笔记 ID 怎么拿 + 执行流程（v2.12.0 起）

### 不用再手填 note_id

**旧体验**：`AI 动作` / `删除` 要一个 19 位 note_id，用户根本不知道。
提示里写「在「分类调整」里展开到「讲」能看到」——**那是错的**：
`inventory --summary` 只给每个讲有几条，不带 ID；而且「讲」≠「笔记」
（实测 660 个讲 / 4322 条笔记，平均 6.5 条）。

**现在两条路**：

| 入口 | 做法 |
|---|---|
| `分类调整` 树 | 「讲」行右侧「N 条 ▾」展开 → 懒加载列出这一讲下每条笔记，每条带「复制 ID」 |
| `AI 动作` 页 | 「从「分类调整」带入选中的讲」→ 把勾选 resolve 成笔记列，点一条直接填进框 |

```
gn.py lecture-notes --kb <库> --course <目录> --book <书> --lecture <讲名>
# 纯本地扫描，返回 [{note_id, title, type}]
```

路由 `GET /plugins/getnote/lecture-notes`（宿主半，**需重启 App**）。
`gn.py resolve` 现在也返回 `titles`（note_id → 标题），界面才能「看着标题挑一条」。

> 复制失败（浏览器拒绝剪贴板）时**不静默**：回退成选中文字 + 明说「只是选中了」。

### 执行流程：两个「造计划」页 + 一个「执行」页

用户反馈「刚跑完找不到」「这两个有点类似」——都是真问题：

- `renderAuto` **以前不渲染干跑结果**（`result` 设了但页面没人读），点「先干跑」像没反应。
- `确认执行` 与 `自动归类` 两页都能写线上，用户不知道刚点的是哪个计划。

现在：

```
分类调整（手选） ─┐
                 ├─→ 计划 ─→ 确认执行（唯一写入口）
自动归类（规则） ─┘              ① 看清单 → ② 干跑 → ③ 真写（连点两次）→ 撤销
```

- 页签顺序 = 工作流顺序；页首常驻「我要：…」场景导航条。
- 自动归类页生成完只给「去「确认执行」干跑 →」。
- 结果卡片在按钮正下方，标题写「干跑结果（线上未动）」/「已写入线上」/「失败」。
- 计划 > 2000 动作时只显摘要，干跑仍打印逐批清单。

## 按人检索与按人看工作内容（v2.10.0 起）

这个账号混着三个人，检索与提纯都必须能**按人切开**，否则 Agent 分不清「谁的事」。

### 什么时候该加 `--owner`

索引里每条都存了 `owner`（`我` / `孩子` / `老婆` / `共用` / `未知`）。
搜的词**可能跨人**时就要加，典型是这些：

| 场景 | 命令 |
|---|---|
| 问孩子的升学，但「强基」「志愿」也会出现在我的转述里 | `gn.py find "强基" --owner 孩子` |
| 找老婆的客服/民航材料，避免捞到我的智能客服案例 | `gn.py find "客服" --owner 老婆` |
| 只找自己的工作方向 | `gn.py find "智能体" --owner 我` |
| 明确想跨人找（如「谁提过 X」） | 不加 `--owner` |

不加 `--owner` 时，搜「强基」出来的多半是孩子的志愿填报 ——
和「我自己的工作」混在一个结果列表里就没法用。

### `agent-brief` 的 `by_owner` 怎么读

`gn.py agent-brief`（或 `/plugins/getnote/brief`）的提纯包里有 `by_owner` 分块，
把「自己记的」那 269 篇按人拆开，每块给：**篇数、未闭合待办数、命中的知识库、理由样本**。

读法三条：

1. **顺序固定**为 `我 / 孩子 / 老婆 / 共用 / 未知`，位置稳定，不用靠名字猜哪块是谁。
2. **只看自己记的那批**。4052 篇摘录是全家一起读的语料，按来源数会占头部
   （「万维钢·精英日课6」926 篇），但自己的计数是 0 —— 那是阅读记录，不是工作方向。
3. **`未知` 块是要人处理的动作项**，不是统计噪音。它附带的理由样本
   （如 `正文含「AI」；正文含「知识库」`）说明为什么判不出来，人据此指定即可。

这样提纯包能分别回答「我在忙什么」和「孩子在准备什么」，
不再把孩子的志愿填报算进我的工作方向。

### 归属判不准时做什么

```powershell
python gn.py personas              # 先看分布 + 未知样本清单（纯本地，不调 API）
python gn.py index                 # 改过 state/personas.json 后重跑，刷新 owner 列
```

`gn.py personas` 是判断归属的**唯一入口**。不要用关键词自己猜，也不要
在没跑它的情况下假设某人归属 —— 猜错的归属会被 `find --owner` 和 `by_owner`
一路带下去，而用户看不出那是猜的。

要改归属就写 `<dataDir>/state/personas.json`（`kb` 知识库归属 / `keywords` 关键词 /
`notes` 按 `note_id` 钉死），格式见 README §11.14。文件不存在或坏了都退回内置默认。

> 未做（不是遗漏，是**已否决**）：多人协作维护同一份库、发布到平台的账号/权限体系、
> 多租户隔离、编辑冲突合并。用户要的是「分类」，不是「多租户」——
> 加账号体系只会增加他一个人的维护负担。否决理由见 `docs/PKM-ROADMAP.md` §4.3。
