## 2. 统计与判断依据

| 项 | 数值 |

- 110 组重复**全部发生在 `BOOKSPACE`**：111 个书架里有 110 个存在同名标签。

- 笔记覆盖：109 组纯冗余覆盖 2162 篇；110 组合计覆盖 2163 篇。

### 2.2 判断依据（scope + count，另加笔记级校验）

按任务要求用 `kb_scopes` 的 `scope` 与两边各自的 `count` 作为主判据；本次另外做了一层**笔记级校验**作为交叉验证：

1. **scope**：该知识库是 `BOOKSPACE`（平台按书自动建的书架）还是 `DEFAULT`（用户自建）。
2. **count**：知识库与标签各自挂了多少篇笔记。
3. **笔记级校验（补充）**：从本地镜像 4321 篇 `.md` 的 frontmatter 解析每篇的「知识库 id」与「标签 id」，比较两边的 `note_id` 集合。

校验结果：

- 镜像解析出的知识库 id 有 122 个、标签 id 有 841 个，与 `ids.json` 完全一致；110 组的 `count` 与镜像集合大小**逐一吻合，零偏差**。
- **109 组**：`note_id` 集合**完全相等**（交集 = 总数，双边差集为空）。
- **1 组**（系统思维）：知识库集合 ⊂ 标签集合，标签多 3 篇。
- 因此 scope + count 的判断被笔记级证据完全证实，没有需要「待确认」的灰色地带。

### 2.3 判定标准

| 判定 | 标准 |

| 纯冗余 | `BOOKSPACE` + 标签 `system` + `note_id` 集合完全一致 → 同一批笔记被书架和标签各装了一遍 |

### 4.2 也不要「直接合并」的 109 组（原因与上不同）

这 109 组虽然是纯冗余，但「合并」这个动作在平台上**根本不成立**，直接做会有副作用：

1. **平台没有「合并知识库/标签」接口**。能做的只有「迁移归属 + 删除一方」，而两边是不同实体（知识库 topic vs 标签 tag），语义不同。
2. **删除不可逆**：删掉任一方都会断掉引用（分享链接、按标签的过滤/自动化）。
3. **电子书书架很可能不可删**：`client.js`（约 2003–2005 行）注释写明「用户无法删除书架」，书架是平台按书自动建的。
4. **system 标签很可能不可删**：`gn.py` 的 `tag-remove` 帮助文案写明「system 类型标签不可删」（本次未实测，见 §6）。
5. **已有反向教训**：`PKM-ROADMAP` §7 明确「不要给删除加批量入口」「不要在没跑 doctor 的情况下执行批量写」。

=> 结论：这 109 组**不要合并**。若一定要治理，正确形式是「**择一保留 + 另一方停用/隐藏**」，而不是合并或删除。

### 4.3 不在本次范围、也不要顺手一起动的

- **11 个 `DEFAULT` 自建库**：无同名标签，与本问题无关。
- **标签「AI」双 ID**：属于「同名不同 ID」问题，不是知识库/标签冗余；按名字操作会静默漏掉一个（见 §5）。

### 4.4 若将来要治理，前置条件（缺一不可）

1. **先全量备份**：跑一次全量只读快照（`getnote_backup`）并校验可读；删除/迁移前再留一份 `undo-snapshot`。
2. **一律按 ID 操作，禁止按名字**：已知标签「AI」同名双 ID；所有目标用 `state/ids.json` 里的 id，不用名字。
3. **先验证「不可删」约束**：用 1 条无关笔记试 `tag_delete` / `kb_remove`，确认 system 标签与 BOOKSPACE 书架的真实可删性，把结论回填到本节。
4. **小批量试点**：先选 1–2 组（建议选 1 篇的，如「决断力」`EJllpZmJ` / `36118436`）干跑，确认撤销能还原归属，再评估是否扩大。
5. **明确「合并」的替代语义**：先决定保留哪一方（建议保留标签、书架只读），再逐条把笔记从另一方移出；**不要删除任何容器**。
6. **治理前后各跑一次 `gn.py ids` + `mirror-check`**，确认 ID 表与线上仍然一致。
