# Mgetbrain 知识管理基础：开发建议

> 面向目标：「补齐 Get笔记 的分类与知识管理短板，让 Mgetbrain 成为个人知识仓库，
> 支持 AI Agent 读取与创新，最终以知识库方式发布、可供家人检索」。
>
> **前提修正（2026-11-20，v2.10.0）**：本文早期把「供多人使用」写成了「多人协作 /
> 团队知识库」，那是**错的理解**。真实情况是**一个 Get笔记 账号、三个自然人共用**
> （我 / 孩子 / 老婆），**维护分类的只有用户一个人**。插件的职责是把内容按人分开，
> 不是做多租户。已改写的章节：§0、§4、§4.3、§6；理由见 §4.3「已否决的替代方案」。
>
> 本文只写**基于实测数据**的判断。凡标注「实测」的，都是在本机 4321 条笔记上跑出来的数字，
> 不是推测。凡标注「未验证」的，都是还没拿到源码级证据的臆断，动手前必须先证伪。

---

## 0. 一句话结论

现在缺的不是功能数量，而是**三层地基**：

1. **可靠的本地镜像**（已具备，但还没有增量与一致性校验）；
2. **稳定的标识与关系**（现在几乎全靠名字字符串做关联，这是最大的隐患）；
3. **可检索的语义层**（现在只有关键词检索，没有向量，也没有面向 Agent 的结构化入口）。

先补这三层，再谈「发布成知识库」；否则功能越多，越难维护。

> 这里**不谈多人协作**。账号是三个人共用的（我 / 孩子 / 老婆），但维护者只有用户一个，
> 所以缺的不是协作机制，而是**归属判定**（这条内容是谁的）——见 §4.3。

## 1. 必须先承认的三条硬约束

### 1.1 平台侧几乎不可逆，删除是单程票

官方 FAQ 自列：「笔记删除后直接彻底删除，未进回收站」「存在严重误删风险」。

**这决定了架构**：所有破坏性操作都必须先在本地留下可还原的副本。
本轮已经落地的最小版本：删除前把正文抓下来写进 `<数据目录>/trash/<note_id>_<标题>.md`
和同名 `.json`，写不成功就**拒绝删除**（`gn.py::_save_to_trash`）。

> 反面代价：这只能保证「内容救得回来」，**不是可逆操作**。
> `note_id` 由服务端分配，重建出来的笔记是新 ID，所有历史链接、标签引用都会断。
> 界面必须这么写，不能让用户以为删错了能一键还原。

### 1.2 写接口粗糙，没有批量事务

`/resource/note/delete`、`/resource/tags/add` 这类接口都是单条、无事务、无幂等键。
一次批量写中途失败，线上就是**部分成功**的状态，没有回滚。

**架构后果**：本插件所有批量写都走「计划 → 干跑 → 确认 → 执行 → 快照」五步，
且执行前自动拍一份归属快照（`undo-snapshot`）。这是目前唯一可行的补偿手段。

> 但注意：**撤销只还原知识库/标签归属，不还原正文**。
> 正文被 `note-update` 覆盖后，现有机制救不回来——这是已知缺口，见 §5.2。

### 1.3 数据构成极偏斜：94% 是课程摘录，不是自己的思考

实测 4321 条：

| 类型 | 数量 | 占比 | 性质 |
|---|---:|---:|---|
| 课程高亮摘录（`ref`/`class_audio`/`link`/`book`） | 4052 | 94% | 别人的话，机器可归类 |
| 自己的记录（`audio`/`meeting`/`internal_record`/`local_audio`/`plain_text`/`img_text`） | 269 | 6% | 自己的话，需要人判断 |

**这一条如果不先想清楚，整个知识管理会做错方向。**

- 对 4052 条摘录做「主题重分类」是**浪费**：它们本来就带着课程/书的结构，
  按来源形态整理（课程 → 章节 → 讲）已经是机器能做的最好结果。
- 只有 269 条自己的记录适合 PARA 那套「按行动性分类」。
  把 PARA 套到 4052 条摘录上，会让「项目」这个盒子塞满别人讲的话，反而失去意义。

**建议**：两条轨道分开管，不要合并。
- 摘录轨：按来源形态 + 关键词/向量检索，目标是「查得到」。
- 自有轨：按 PARA + 渐进摘要，目标是「用得上」。

## 2. 三个真正的地基缺口（按优先级）

### 2.1 【P0】去掉「用名字做外键」

**现状（实测）**：`kb_scopes.json` 里 110/122 个知识库名与标签名重复；
全文只有 1 条笔记同时属于 2 个知识库。所有关联都靠名字字符串。

**问题**：改一个知识库名，所有靠名字做的映射全部失效，而且**不会报错**——
只会静默变成「找不到」。这类 bug 最难查。

**做法**：
1. 建一张 `ids.json`：`{kb: {name → id}, tag: {name → id}, course: {...}}`，
   每次 `inventory` 时刷新，作为唯一真实的 ID 表。
2. 所有内部关联、计划文件、撤销记录**一律存 ID**，名字只用于显示。
3. 加一致性检查：`doctor --check-ids` 报告「名字变了但 ID 没跟上」的条目。

**验收**：改掉一个知识库名后，重跑 `inventory` + `doctor`，能报出受影响的计划文件列表。

> **2026-11-19 进展：第 1 步已落地，第 2–3 步未做。**
> `gn.py ids` 已能扫全部镜像生成 `state/ids.json`（名字 → id），并实测抓到
> **标签「AI」对应两个不同 ID**（36117013 / 36111209）——这正是「按名字当外键」
> 会静默漏一半的真实例证。但**内部关联还全是名字**：计划文件、撤销记录都没切换到 ID。
> 所以这条只完成了「把问题摆到明面上」，没完成「把问题修掉」。

### 2.2 【P0】镜像要能增量更新并自证一致

**现状**：`data-getbrain/current/` 下 4321 个 `.md`，靠 `download --into current` 增量刷新
（只重写 `updated_at` 变了的）。但**没有校验**：不知道本地和线上是否一致。

**问题**：本地镜像是所有只读分析的基础。镜像一旦偏差，
后面所有「按本地算出来的计划」都会打错地方——而且是批量打错。

**做法**：
1. 每份 md 的头部写入 `updated_at` 与 `content_hash`。
2. `doctor --verify-mirror`：抽样（或全量）拉线上 `updated_at`，与本地比对，
   列出「线上更新了但本地还是旧的」「线上已删但本地还在」两类。
3. 提供 `download --repair` 只修偏差项。

**验收**：手工在 App 里改一条笔记，`doctor --verify-mirror` 能指出来，`--repair` 能修好。

### 2.3 【P1】给 Agent 一个稳定的读取入口

**现状**：`context-pack` 能打包一批笔记给模型读。但它按「选了哪些」打包，
没有一个**面向工作内容**的视图。

目标是「支持 AI Agent 读取和创新、理解我的主要工作内容」，
那 Agent 需要的是：**这件事我做过什么、结论是什么、有哪些未完成**，
而不是「这是第 100 到第 140 条笔记」。

**做法**：
1. `agent-brief --topic <名>`：输出一份结构化摘要，包含
   - 该主题下的自有记录（269 条那部分）按时间倒序；
   - 关键结论（从渐进摘要的 Layer 3/4 取）；
   - 未闭环项（`meeting_todos` 里没勾的）。
2. 一份 `SCHEMA.md` 说明字段含义，让 Agent 不用猜。
3. 加 `--format json` 与 `--format md` 两种输出。

**验收**：给定一个真实工作主题，`agent-brief` 的输出能让另一个人（或另一个模型）
不看原始笔记就答出「这件事到哪一步了」。

> **2026-11-19 进展：`agent-brief` 已落地（不带 `--topic`，改按时间/来源聚合）。**
> 实测输出 431 条未闭合待办、时间分布、自己的主题、最近动态。
> `--json` 已支持，`SCHEMA` 尚未单独成文（字段含义写在 SKILL.md）。
>
> **最关键的实测发现**：269 篇自己记的笔记里 **219 篇（81%）没进任何知识库**，
> 60 篇只有「得到」或载体标签。剔除这些无效标签后，真正有主题的不到 10 个
> （高考志愿填报、强基计划、AI、航空服务、击剑、民航服务…）。
> 也就是说：不是「AI 读不懂」，是**这些笔记本身就没有被归过类**。
> 这直接决定了下一步该做什么——先把 219 篇归位，比做任何检索都有效。

> **关键修正（实测推翻了原计划）**：原设计写「自有记录 269 条按时间倒序」，
> 但真正的问题是**这 269 条几乎没有主题归属**。光按时间排，Agent 只知道
> 「用户记了很多零散笔记」，仍不知道他主要做什么。所以实现里加了 `own_topics`
> （标签 + 知识库聚合），并且**把 4052 篇摘录排除在「工作内容」之外**——
> 它们按来源数会占据头部（万维钢 926 篇），但自己的计数是 0，那是阅读记录不是工作方向。

> 另：原计划写「未闭环项从 `meeting_todos` 取」，实测该字段不存在于镜像结构里；
> 真实位置是 AI 总结里的 `### 📋 待办事项` 小节。已按实际结构实现。

## 3. 分类与知识管理：补齐短板

### 3.1 已落地的三项（本轮）

| 短板 | 现在怎么做 | 关键设计 |
|---|---|---|
| 看不清楚（白底白字按钮） | 全部改用 `--dsw-alias-*` 语义色 | 前景色用会随主题翻转的 `label-primary-foreground`，填充用 `state-business-primary`；硬编码 `#fff` 清零 |
| 知识库 ID 要手填 | 下拉选择 + 「新建库」输入框 | `inventory` 本来就返回 `id`，界面一直没接；现在接上，且新建走 `topicName`（`kb_ensure` 按名幂等） |
| 不能删除 | 独立的「删除区」，默认收起 | 四道闸门：展开 → 勾「我知道不可恢复」→ 干跑 → 二次确认；删前必须存 `trash/` |
| 不能删除 | 独立的「删除区」，默认收起 | 四道闸门：展开 → 勾「我知道不可恢复」→ 干跑 → 二次确认；删前必须存 `trash/` |
| 笔记 ID 看不到（要手填） | 「讲」可展开到笔记，每条带「复制 ID」；AI 动作页可从勾选直接带入 | 「讲」≠「笔记」（660 讲 / 4322 笔记，平均 6.5 条），所以必须展开到笔记层，见 §3.2(d) |
### 3.2 还没做，但明确该做

**（a）合并笔记 —— 已实装（v2.9.0，本节原写「还没做」已过时）**：
`gn.py merge` + `POST /plugins/getnote/merge` + 界面「合并」页。
平台没有合并接口，所以做法是「读两条正文 → `note-save` 建新笔记（正文拼接 + 保留两份原始链接）→ 旧的不自动删」。
新笔记是新 ID、历史引用会断，界面必须先显示这一点；删旧另开一步（见 §8）。
**（b）渐进摘要 —— Layer 3 已实装，Layer 4 只给模板（v2.11.0）**：
`gn.py summarize` 把 Layer 3（关键词句自动提取、加粗）写进 `<dataDir>/summaries/<note_id>.md`，
同文件留 Layer 4 模板（用自己的话，必须人写）。
**不写回平台**：写正文是 `note-update` 的覆盖语义，风险极高（见 §5.2）。

**（c）标签与知识库的冗余治理 —— 报告已出（v2.11.0）**：
实测 110/122 个知识库名与标签名重复。逐条判断见 `docs/REDUNDANCY-REPORT.md`：
**109 组是纯冗余**（全部落在电子书书架 BOOKSPACE，两边 note_id 集合完全相等），
**1 组必须保留**（「系统思维」标签比书架多 3 篇）。**不要直接合并**，前置条件写在报告 §6。
**（d）笔记 ID 不用手填 + 执行流程重组（v2.12.0）**：
树里「讲」行右侧「N 条 ▾」可展开，懒加载列出这一讲下的每条笔记，每条带「复制 ID」；
`AI 动作` 页新增「从「分类调整」带入」，把勾选 resolve 成笔记列，点一条直接填。
新命令 `gn.py lecture-notes`（纯本地）、新路由 `GET /plugins/getnote/lecture-notes`（宿主半，需重启 App）；
`gn.py resolve` 顺带返回 `titles`（note_id → 标题），否则「看着标题挑一条」做不到。

执行流程固定成「两个造计划页 + 一个执行页」：分类调整 / 自动归类都只生成计划，
**干跑与真写只在「确认执行」页**；页首常驻「我要：…」场景导航条。
修掉的真 bug：`renderAuto` 以前**不渲染干跑结果**（用户「刚跑完找不到」）；
两页都能写线上导致「不知道刚点的是哪个计划」。

## 4. 一个账号三个人，与「以知识库方式发布」

目标里提到「可以供多人使用」「以知识库方式发布」「便捷检索」。
**「供多人使用」指的是一个共享账号里三个人的内容都能各自读到、各自检索**，
不是多人协作编辑。这三件事的技术前提是**导出格式 + 归属判定**，不是权限系统。

### 4.1 现在就能做的：静态知识库导出

> **交付状态（2026-11-20，v2.9.0，v2.10.0 补归属轴）**：`publish` 命令已实装，
> 但不是本节当初设想的三件事，实际做法与理由见下。三件事的对照：
>
> | 本节建议 | 实际做了 | 差异原因 |
> |---|---|---|
> | 稳定 slug | 用标题 + 冲突编号 | 标题可读性对「发给别人读」比 id 重要；重名已处理 |
> | `index.json` + `README.md` | 只做了 `index.html` | 目标是**人读**，不是机器读 |
> | 双链 | **没做** | 正文里跨笔记引用极少，收益低于成本 |
> | **归属（persona）轴**（v2.10.0 新增） | `personas` / `find --owner` / `agent-brief by_owner` | 本节没提，但这是「供多人使用」的真实落点：一个账号三个人的内容必须能按人切开，否则检索与提纯都分不清「谁的事」 |
>
> 另外加了本节没提的：**纯前端搜索页**（`search.html`，数据内联）。
> 为什么不做 `mkdocs`/`vitepress`：它们要 Node 工具链和构建步骤，
> 而「拿到目录双击就能用」是更硬的要求。零外部依赖是实测的（外部引用数 0）。
>
> 检索侧本节也没提：实装了**本地 sqlite FTS5 + 中文 bigram 分词**的
> 字面检索（`gn.py find`），170 ms 一次、离线、可按库过滤。
> 这与下面 4.2 说的向量检索是**两件事**，向量仍未做。

`export` 命令已在（**注：它打包的是工具包脚本，不是知识库内容**）。建议补三件事：

1. **稳定的 slug**：文件名不要用标题（标题会变、会重名），用 `note_id` + 短 slug。
2. **索引文件**：`index.json`（机器读）+ `README.md`（人读），
   列出每篇的分类、来源、更新时间。
3. **双链**：把笔记正文里出现的其它笔记 ID/标题转成相对链接，
   导出成静态站点（`mkdocs` 或 `vitepress`）即可发布。

> 为什么先做静态：多人协作需要权限、冲突解决、审计，那是另一个工程 ——
> 而且**本插件明确不做**（见 §4.3「已否决的替代方案」）。
> 「发布成可检索的知识库」只需要一次导出：**先给能用的，不碰协作。**

### 4.2 向量检索：先做本地，不做服务

`dsh-rag` 插件已经证明本地向量库可行（SQLite + 嵌入模型）。
建议同样路线：
- `rag.py ingest` 吃 `current/` 的 md；
- 用同一套 `rag_search` / `rag_ask` 工具接口，不要另造一套。

> **交付状态（2026-11-26，v2.11.0）**：本节原设想「复用 `dsh-rag` 工具面」。实装的是**本地稀疏向量（TF-IDF）**
> （`gn.py vec-index` / `vec-search`，存 `state/vec.db`），纯标准库、不联网、可解释。
> 它**不是语义嵌入**：同义不同词（「沟通」 vs 「交流」）仍会漏。要真语义检索仍需 embedding 模型，
> 而那是 `dsh-rag` 的路线（云端 embedding + Zilliz），与本插件「零依赖、离线」的硬约束不一致，故不并入。
> 不要一开始就上云服务：① 笔记是私人数据；② 4321 条的量级本地完全跑得动；
> ③ 真需要多人同时写同一份库时再考虑服务端 —— 但那是本插件**已否决**的方向（§4.3），
> 现在只需要「每个人能读到属于自己的那部分」。

### 4.3 一个账号三个人的真实难点（不是技术）

先纠正本节原先的错误前提。原来写的是「实测只有 1 条笔记同时属于 2 个知识库，
说明使用模式是单人单线，多人场景会立刻遇到权限/并发/审批」——**前提就错了**。
用户原话：

> 多人维护这个你理解错了。我是说我这个 get 笔记是多人用一个账户，所以内容会比较杂，
> 有学习的（孩子）也有工作和 AI 思考的（我的）还有部门会议的（老婆的）。
> 这些信息是让你做好分类的背景信息。维护（做分类）主要还是我一个，
> 不是这个插件要多人使用做处理。

所以真实的难点不是权限、不是并发、不是审批，而是下面两件事。

**（a）难点一：归属判定（这条内容是谁的）**

一个账号里混着三个人的内容，本地却没有任何字段告诉你「这条是谁的」：

| 归属 | 内容主线 | 命中知识库（实测篇数） |
|---|---|---|
| 我 | AI 平台、算力、大模型、智能体、国航数字化、飞书、知识管理、数据治理 | `aisnip`(10)、`working`(3)、`icosa`(3)、`projectu`(1) |
| 孩子 | 高考、强基计划、志愿填报、院校专业、高二高三、语文作文提分、击剑训练、大学新生课程 | `fencing`(7)、`university`(6)、`chinese`(1)、`nemomeng的知识库`(1) |
| 老婆 | 民航服务质量管理、客服投诉处理、国航客服中心例会、暑运、民航法修订 | `susan`(16) |
| 共用 | 家里一起读的课程与书本摘录 | `family` 默认为「共用」；绝大多数摘录也从这里出 |
| 未知 | 本地信号不足 | 不硬猜，留给人来指 |

规模上，全账号 4321 篇里**自己记的只有 269 篇（6%）**，其中**只有 50 篇进了知识库，
219 篇没有任何知识库**。剩下 4052 篇（94%）是课程与电子书摘录 —— 那是全家一起读的语料。

判错的代价是具体的：Agent 会把「孩子的志愿填报」当成我的工作方向，
把「老婆的客服中心例会」当成我的部门会议，然后拿一堆别人的事给我出主意。

**（b）为什么关键词-only 不行（实测数字）**

纯关键词判定 269 篇自己记的，只能分到：

| 我 | 孩子 | 老婆 | 歧义 | 未知 |
|---:|---:|---:|---:|---:|
| 67 | 81 | 20 | 4 | **97** |

**97 篇（36%）判不出来**，4 篇两边都像。根因是关键词天然串台：

- 「国航」——我的国航数字化 与 老婆的国航客服中心；
- 「客服」——我的智能客服案例 与 老婆的投诉处理；
- 「训练」——大模型训练 与 孩子的击剑训练。

把词表收窄只能减少误判、会增加「未知」；放宽则错归属。**单靠关键词两头不讨好。**

所以实装的是**三种信号叠加**（`gn.py::_owner_of`）：

| 信号 | 权重 | 理由 |
|---|---|---|
| 知识库命中 | +12 | 人手动把笔记放进某个库，是最可靠的意图信号 |
| 标题关键词 | +5/个（最多 3 个） | 标题是作者自己起的，噪声最低 |
| 正文关键词 | +1/个（最多 5 个） | 正文长，单个词说服力要压低 |
| 按 `note_id` 手动钉住 | 最高优先 | 人说了算，覆盖一切打分 |

分数不够时：摘录判「共用」（全家一起读的），自己记的判「**未知**」。
两候选同分也判「未知」。**这条代价必须留在路线图里**：归属永远不可能全自动，
它注定是「机器给初判 + 人补最后 20%」的工作流。

**（c）难点二：命名污染（名字当外键的静默失效）**

这是本项目最隐蔽的一类问题，全部实测：

| 现象 | 实测 | 后果 |
|---|---|---|
| 知识库名与标签名重复 | **110 / 122** 个知识库名同时是标签名 | 同一个概念存两份，「改一处」永远改不全 |
| 书架的「知识库」其实是电子书 | 122 个库中 **111 个是 `BOOKSPACE`**（得到电子书自动书架） | 看着像「我有 122 个知识库」，实际只有 **11 个**是自建 |
| 同名不同 ID | 标签「AI」有**两个** id：`36117013` / `36111209` | 任何按名字做的标签操作**只会命中一个**，另一个静默漏掉，且不报错 |

第三条是真 bug：它不抛异常、不写日志，只是少改一半。所以已落地 `gn.py ids`
（扫镜像生成唯一 ID 表，2 秒，纯本地），但**内部关联还全是名字** ——
计划文件、撤销记录都没切到 ID，这条只完成了「把问题摆到明面上」。

**（d）为什么「多人协作 / 权限 / 冲突合并」被明确否决**

这是「已否决的替代方案」，不是待办：

| 被否决的方案 | 否决理由 |
|---|---|
| 账号体系 / 多租户隔离 | 只有一个账号，三个自然人共用。加账号体系要**先把内容拆到三个账号**，那是一次高风险的大迁移，且平台不支持转移笔记归属 |
| 角色与字段级权限 | 平台没有这个字段，本地造一套权限只能管住本地镜像，管不住 App |
| 编辑冲突合并 | 平台写接口**无事务、无幂等、无版本号**（§1.2），并发写只会产生「部分成功」，合并在没有版本的前提下无法定义 |
| 审批流（删除/改名） | 维护者只有一个人，自己审自己没有意义，只增加点击次数 |

**根本判断**：用户要的是**分类**，不是**多租户**。他要解决的是「我一个人的账号里
混着三个人的东西，帮我分清」，而不是「三个人一起编辑同一份知识库」。
加账号体系只会增加他一个人的维护负担 —— 那是**把问题做大**，不是解决。

**（e）维护成本压在一个人身上，界面必须回答「这条该归谁」**

这是本节对界面/命令的硬要求，也是 v2.10.0 的设计依据：

1. **「未知」必须可见**：`gn.py personas` 会打印未知样本清单（带 `note_id` 与判定理由），
   侧边栏有归属分布块。用户要能一眼看到「还剩多少篇没指」——
   当前实测 78 篇待指 + 20 篇空白（空白不用管，所以界面把两者分开显示，
   不能合成一个 98 让人觉得有 98 件事要做）。
2. **「未知」必须能一键钉住**：`<dataDir>/state/personas.json` 的 `notes` 支持按
   `note_id` 直接指定归属，优先级最高（覆盖打分）。不需要重跑复杂流程。
3. **不许静默给猜测**：判不出来就留「未知」，**不要塞一个看起来合理的归属**。
   错的归属会被 `find --owner` 与 `agent-brief by_owner` 一路带下去，
   而用户完全看不出那个结论是猜的。可见的空白比隐藏的错误便宜得多。
4. **理由必须落进输出**：`why` 返回中文理由（如 `知识库「susan」`、`标题含「强基」`），
   人能复核才可能纠正。没有理由的归属等于猜。

## 5. 已知缺口（不遮掩）

### 5.1 撤销不还原正文

`undo` 只还原知识库/标签归属。`note-update` 覆盖正文后无法撤销。
**缓解**：任何改正文的操作，执行前把旧正文写进 `trash/`（复用删除那套备份）。

### 5.2 删除不可逆

已用本地 `trash/` 兜底，但那是「内容救得回来」，不是「操作可撤销」。
重建后 `note_id` 变，历史引用断。

### 5.3 批量写是部分成功的

平台无事务。100 条里第 50 条失败，前 49 条已经在线上。
**缓解**：计划文件本身就是「已做到哪一步」的记录；`apply` 失败后可以按计划文件续跑，
但要先 `doctor` 确认当前线上状态，不能盲目重跑。

### 5.4 聚合类数字口径不一

`inventory` 的 `count`、镜像里的实际文件数、线上 `list` 的总数，三者偶尔不一致
（未验证根因，怀疑是分页与软删除的差异）。
**在依赖这些数字做批量决策前，必须先跑 `doctor` 核对。**

## 7. 不要做的事

1. **不要按主题重分类那 4052 条摘录**。它们有来源结构，重分类是破坏信息。
2. **不要给删除加「批量」入口**。单程票操作必须一条条来。
3. **不要把 note_id 当成必填输入框**。v2.9.0 先从勾选解析（`/resolve`），v2.12.0 再补「讲展开到笔记 + 每条可复制 ID」与「AI 页从勾选带入」——两条路都不用人手填 19 位数字。
4. **不要用 `--dsh-*` 变量当颜色**。实测 175 个全是布局尺寸，没有一个颜色。
5. **不要在没跑 `doctor` 的情况下执行批量写**。平台无事务，错了没有回滚。
