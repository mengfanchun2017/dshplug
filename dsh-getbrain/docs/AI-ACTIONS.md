# AI 动作（发芽 / 审问）设计

> 状态：2026-11-18。实装位置：`gn.py sprout` / `gn.py context-pack` / `client.js` 的「AI 动作」页。
> 一句话：**平台只让查不让生成；生成由 DSH 的 AI 做，提示词你可以改。**

---

## 1. 先摆事实：官方到底开了什么

我逐个探过（全部为只读 GET，实测记录在 `logs/*.jsonl`）：

| 端点 | 结果 | 说明 |
|---|---|---|
| `GET /resource/note/sprout?id=<note_id>` | **200** `{"sprout": null/"…", "has_sprout": bool}` | 唯一存在的发芽端点 |
| `POST /resource/note/sprout` | 404 | 不能通过 API 生成发芽 |
| `/resource/ai/sprout`、`/resource/ai/ask`、`/resource/ai/chat`、`/resource/ai/summary`、`/resource/note/ask`、`/resource/note/question`、`/resource/note/interrogate`、`/resource/note/related` 等 13 个候选 | 404 | 都不存在 |
| `/resource/note/sprout` 缺 `id` 时 | `10000 id is required` | 反证端点真实存在（不是路由兜底） |

**结论**：
- **发芽**：平台侧只能**读**已有结果，不能**生成**。
- **审问**：平台侧完全没有这个端点。

所以这两件事的正确做法是：
1. 平台已有发芽 → `gn.py sprout` 取回来直接展示；
2. 平台没有 → 由 **DSH 的 AI** 基于 `gn.py context-pack` 生成；
3. 生成结果**只作为建议呈现**，不自动写回笔记。

## 2. 「发芽」和「审问」到底指什么

不是抽象概念，有用户原话作依据。

**发芽**（用户自己的用法，来自笔记 `1918061344897183496`）：

> 「一会儿吧，那个让发芽一下，看能不能把沟通和另外两个做一个补充」

即：给定一条已有的记录，**联想出它没说的那部分** —— 补全、延伸、指出缺口。
对应产品侧描述（GetSeed AI 录音卡）：「AI 主动生成一份发芽报告，基于用户记录的内容联想相关知识点」。
来源：<https://weqoocu.com/3295.html>（2026-01-01）

放在知识管理理论里，发芽 = 渐进式总结的 **Layer 5（重混/延伸）** + Evergreen notes 的 **associative（联想）**而非层级。

**审问**（本插件定义，平台无此功能）：

对一条笔记**提问**，逼出「你到底懂没懂」。这是费曼技巧 / 苏格拉底提问的工程化：
- 不是让 AI 总结（总结是 AI 的产出）
- 而是让 AI 出题/追问，**答案要你自己想**
- 对应 Progressive Summarization Layer 4「用**自己的话**写」

两者的根本区别：

| | 发芽 | 审问 |
|---|---|---|
| 方向 | 向外扩（这条还能连到什么） | 向内挖（这条我真懂吗） |
| AI 产物 | 关联/延伸/缺口清单 | 问题清单（不给答案，或答案折叠） |
| 写入 | 不写 | 不写 |

## 3. 为什么必须有 `context-pack`

AI 只拿到一条笔记就发芽，会退化成「泛泛而谈」。真实需要三类上下文：

1. **同系列相邻的讲** —— 这门课前后的脉络（`siblings`）
2. **跨系列的相关段落** —— 别的课/别的录音聊过同一件事（`related`）
3. **关键词** —— 用来判断「相关」的依据，也让用户知道相关性是怎么算出来的（`keywords`）

`context-pack` 干的就是从本地 4321 个 md 里凑齐这三样，**不发网络请求**，纯本地。

### 关键词质量：踩了三次坑才修对

这是真实记录，不是理论：

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 滑窗取 2–4 字 | 抽出「整体来讲」「的东西」「后续再继」→ 相关段落全是噪声 |
| v2 | 加填充词黑名单 + 提高频次门槛 | 好一点，但仍有「这一块」「整体来」→ 因为滑窗不认词边界 |
| **v3（现在）** | ①先按标点切短句；②片段不得含虚词、不得以数词/代词开头；③片段不得是填充词的子串；④用全库文档频次（df）剔除「到处都有」的泛词 | 抽到「硬技能」「软技能」「数据壁垒」「专业领域」 |

v3 的效果（实测同一条笔记）：

- 修前：8 个"相关"，全是「整体来讲」误命中击剑训练、院校选择
- 修后：**1 个相关** ——「数字化战略推演」命中「硬技能」「软技能」，是真相关

**宁可少，不要假。** 这是本插件一以贯之的取向。

## 4. 提示词：可以改，且改在明处

这是你要的「甚至可以基于这个开发自己的提示词和点击按钮」。

设计：**提示词不是硬编码在 JS 里，而是存在数据目录**，界面里可读可改。

```
dataDir/prompts/sprout.md     ← 发芽提示词
dataDir/prompts/interrogate.md ← 审问提示词
dataDir/prompts/actions.json   ← 自定义按钮（名字 + 用哪个提示词 + 作用于什么）
```

首次使用时自动创建默认文件，之后**你改了就生效，不用改代码**。

内置三个按钮：

| 按钮 | 作用 | 提示词 |
|---|---|---|
| 发芽 | 联想/补全/指缺口 | `sprout.md` |
| 审问 | 出题逼理解 | `interrogate.md` |
| 连线 | 找跨系列共同点 | `link.md` |

### 为什么不用「让 AI 自己决定做什么」

这个面板会被反复点击。隐式行为的代价是：用户不知道点了会发生什么、也不知道该期望什么。
**每个按钮绑定一份可见的提示词**，点之前就能看见它会怎么问 AI。

## 5. 结果怎么回写（当前：不写）

| 选项 | 现状 | 理由 |
|---|---|---|
| 结果只在界面显示 | ✅ 当前 | 零风险 |
| 存成一条新笔记 | ⏳ 有 `note_save`，但未接 | 会产生大量 AI 笔记，先不默认 |
| 追加到原笔记 | ❌ 不做 | `note_update` 改正文不可撤销（见 UNDO-DESIGN §7） |

**「存成笔记」的闸门**（将来要做时）：
- 必须显示完整正文预览
- 必须标明「AI 生成，非原始记录」
- 必须走 `/apply` 的 confirm 双闸门

## 6. 诚实边界

- **发芽的平台端生成做不了**：只有 GET 查询，POST 404。要平台侧发芽必须在得到 App 里点。
- **审问完全是本插件造的概念**：官方没有，也没有证据表明官方将来会有。这是设计选择，不是平台能力。
- **`context-pack` 的相关性靠关键词命中数**，没有语义向量。同义不同词（「沟通」vs「交流」）会漏。这是刻意选择：本地实现、零依赖、可解释。要语义检索需要接 embedding，那是另一个工程。
- **siblings 经常是 0**：因为很多笔记的"课程"就是它自己（如录音类）。这不是 bug，是数据形状。
- 提示词文件是**本地明文**，不含任何凭据，可以进 Git；但 `actions.json` 里如果写了敏感内容，用户自己要负责。
