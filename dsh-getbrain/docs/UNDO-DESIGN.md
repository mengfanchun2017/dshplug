# 撤销设计（Undo for Mgetbrain）

> 状态：2026-11-18 设计，随代码实装。
> 一句话：**每次写入前先把「原状」存下来，撤销就是把原状放回去。**

---

## 1. 为什么不能只靠反向操作

直觉做法是「加了就删、删了再加」。实际不行，因为官方 API 的语义有坑：

| 操作 | 实际语义 | 天真反向 | 为什么错 |
|---|---|---|---|
| `kb_batch_add`（加库） | **只加不移**。一条笔记可同属多个库 | `kb_remove` | 如果笔记**原本就在**这个库，`kb_remove` 会把它从原来的库里也踢掉 → **丢数据** |
| `tag_add` | 追加标签 | `tag_delete` | 如果标签**原本就有**，删掉就丢了 |
| `kb_remove` | 从某库移除 | `kb_batch_add` | 这个可逆，但前提是知道它原本在不在 |
| `note_update --tags` | **整体覆盖**标签 | 无 | 必须存旧标签全量 |

**结论**：不知道「改动前是什么样」，就不能安全撤销。
所以撤销的第 0 步不是记「我做了什么」，而是记「**它本来是什么**」。

实测依据：`GET /resource/note/detail` 返回的 `topics` 里带 `id`/`name`，
`tags` 里带 `id`/`name`/`type`。这两样足以精确还原归属，不需要整篇正文。

## 2. 数据结构

每次 `apply`（真写，非 dry-run）在执行前生成一份 **undo 记录**：

```jsonc
{
  "version": 1,
  "created_at": "2026-11-18T17:20:00+08:00",
  "plan_file": "state/plan.pending.json",
  "pre_state": {
    // note_id -> 改动前的归属（只记要动的笔记，不是全库）
    "1887299012080602912": {
      "topics": [{"id": "XyYvDrJN", "name": "icosa"}],
      "tags":   [{"id": "52186382", "name": "录音笔记"}]
    }
  },
  "applied_ops": [
    {"op": "kb_batch_add", "topic_id": "abc", "note_ids": ["1887..."]}
  ],
  "status": "open"   // open = 可撤销；undone = 已撤销；partial = 部分撤销
}
```

存到 `dataDir/state/undo-<时间戳>.json`。

**为什么不存全量**：4321 条全量快照约 891KB（已有 `backup` 命令干这事）。
撤销只需要「这次动了哪些」，几百条以内，秒级可写。

## 3. 撤销怎么算

对每条被改动的笔记，比较 **pre_state** 和 **当前状态**：

```
对每个 topic_id：
  before = pre_state.topics 里有它？
  now    = 当前 detail.topics 里有它？
  before && !now  -> 需要 kb_batch_add 补回去
  !before && now  -> 需要 kb_remove 拿掉
  before && now   -> 不用动
  !before && !now -> 不用动
```

标签同理（用 `tag_add` / `tag_delete`）。

**这个算法是「状态收敛」而不是「逆操作」**，好处：
- 中途有人手动改过，撤销不会把他改的覆盖掉（只修正我们碰过的部分）
- 重复执行撤销是幂等的（第二次算出来全是「不用动」）

---

## 4. 安全边界（硬规则）

1. **只有真写才生成 undo**。dry-run 不生成（没改东西，撤销没意义）。
2. **撤销本身也要确认**：`undo --plan <undo文件> --confirm UNDO`。
3. **撤销绝不删除笔记**。只动归属（库/标签）。`note_delete` 不进撤销体系 —— 平台删了就进回收站，撤销不该假装能救回来。
4. **超过 500 条的撤销要额外确认**（`--allow-large`），防止一次点错回退整库。
5. **撤销记录只增不改**：`status` 字段从 `open` → `undone`，不物理删除文件。审计要留痕。

---

## 5. 界面上怎么呈现

- 「确认执行」页真写成功后，多出一行：**「已记录可撤销（N 条）→ 撤销」**
- 点撤销 → 弹出摘要（会改回哪些笔记、涉及哪些库）→ 再点一次才执行（双点，和真写一致）
- 撤销成功 → 该行变成「已撤销 · 时间」，不可再点
- 「执行日志」页另有一个「可撤销批次」列表，覆盖历史批次

**为什么不给一个全局「撤回上一操作」按钮**：
这个面板能误触，而「上一操作」是隐式的 —— 用户以为是刚才那次，实则可能是别处改的。
显式列出「哪一批、改了什么、多少条」，误点概率低得多。

---

## 6. 已否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 只记操作日志，靠逆操作回退 | 上面 §1 的三个坑，会丢归属 |
| 每次写前全量 backup | 30 秒起，且占空间；4321 条的 `backup` 已是单独命令 |
| 用平台自身的回收站 | 只管删除，不管「从知识库里移除」；`kb_remove` 不进回收站 |
| 无限撤销栈 | 每条笔记只保留最近一次 pre_state，多层栈在跨批次时会互相覆盖，且难以解释给用户 |

---

## 7. 诚实边界

- 撤销**只能还原归属（知识库/标签）**，不能还原笔记正文（`note_update` 改的内容不存旧文）。
  要做正文撤销，得在 pre_state 里存全文 → 体积大 3 个数量级，暂不做。
- 如果撤销期间平台侧删了某条笔记，撤销那条会报 `10500 note_not_found`，跳过并计入 `skipped`。
- 撤销**不认识**「平台自动归类」或 App 内的改动 —— 它只认本插件写的 undo 文件。
